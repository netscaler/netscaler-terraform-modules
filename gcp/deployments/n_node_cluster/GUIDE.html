The one rule

Edit terraform.tfvars. Nothing else.

Every knob worth turning is a variable, and every variable has a documented default in variables.tf. The thirteen .tf files are the machinery; terraform.tfvars is the control panel. In normal use you should never need to open a .tf file at all — not even to change the number of nodes.

If you find yourself wanting to edit a .tf file, that is a signal to check the script reference first — the setting you want probably already exists as a variable.

Changing the cluster size

One line:

# terraform.tfvars
node_count = 5

That single number drives everything:

What it controlsHow
GCE instancescount = local.node_count on google_compute_instance.adc
NSIPs (management)nsip_host_offset + node id, out of management_subnet_cidr_block
Client / server addressesdata_host_offset + node id, out of their subnets
External addressesone per node, per NIC, when the corresponding assign_*_external_ip is true
Cluster node blocksdynamic "clusternode" over local.cluster_nodes
Cluster prioritiescluster_priority_base + node id
Spotted SNIPsone citrixadc_nsip per node per subnet, ownernode = node id
Password resetscount = node_count on terraform_data.password_reset

Valid range is 1 to 32. 32 is the NetScaler cluster limit, not a limit of these scripts. node_count = 1 is legal and gives a single-node cluster with a CLIP — useful for testing the plumbing cheaply.

32 nodes is the one size that needs a second setting changed

The ADC accepts cluster priorities 0 to 31 inclusive, and this configuration assigns cluster_priority_base + node_id. So the real constraint is:

node_count <= 32 - cluster_priority_base

At the old default of cluster_priority_base = 1, asking for 32 nodes needs priorities 1–32 — and 32 is one past what the appliance takes. The plan is rejected before anything is built:

cluster_priority_base 1 with node_count 32 needs cluster priorities 1 to 32,
but the ADC only accepts 0 to 31. Set cluster_priority_base to 0 or lower for
32 nodes; a 32-node cluster uses the whole range and requires 0.

The fix is one line — cluster_priority_base = 0, which is what this deployment now uses. Priority 0 carries no special meaning; lower simply wins the CCO election, so node 0 still leads. (NetScaler command reference, add cluster node: "Default value: 31 Minimum value: 0 Maximum value: 31".)

What 32 nodes costs, and what no precondition will tell you
  • 256 vCPUs. 32 × n2d-standard-8. GCP rejects this mid-apply, after it has begun creating instances — quota is not visible at plan time.
  • 32 regional external addresses, because assign_client_external_ip is true. The default per-region quota is far smaller. Set it to false or raise the quota.
  • Hours, not minutes. Node joins are sequential and each one reboots the node, so formation scales with node_count. The provider's node_add_total_timeout is per node-add rather than for the whole set, so it does not need raising — but cluster_watch_timeout does, or the watcher stops reporting in the first fraction of the run. It is 14400 (4 h) here for exactly that reason.

Check both quotas before starting. A 32-node apply that dies at node 19 on a quota error leaves you with the teardown problem, not a cluster.

Why providers.tf still has 32 near-identical blocks

The password reset used to be 32 citrixadc_password_resetter blocks. That resource has no endpoint attribute, so the only way to aim one at a node was a provider alias — and Terraform cannot generate aliases. The reset is now a single terraform_data.password_reset counted by node_count (see why), and nothing uses the aliases any more.

They stay because Terraform needs a resource's provider configuration to drop it from state, and a state file from before the change may still hold old resetter entries. Every alias is do_login = false and unused slots point at loopback — they cost nothing and dial nothing.

You do not read or edit providers.tf. It is generated machinery.

Resizing a cluster that already exists

Changing node_count on a live deployment adds or removes nodes in place. Growing is cheap. Shrinking removes the node from the CLIP first, then destroys the VM; node 0 (the CCO) goes last.

Grow one node at a time the first time

Only the 3-node create path has actually been applied end to end. The in-place resize path goes through citrixadc_cluster's Update, which is far less exercised than its Create. Go 3 → 4, confirm with show cluster node, then go further.

The backplane goes on 0/1. This is the opposite of on-prem practice.

A VPX on GCP auto-configures only its NSIP, from nic0. Interfaces 1/1 and 1/2 come up with no IP at all. A backplane with no address cannot carry a heartbeat, so a node given 1/2 joins, sits at (Adding), and the apply fails 30 minutes later with a bare "timeout waiting for cluster operation to complete".

Fixing it after the fact is impossible from Terraform: citrixadc_cluster does not return until every node reports ACTIVE, so the SNIP that would give the node an address sits unapplied behind the very resource waiting for it. This cost two full apply cycles — see Issues & fixes.

Secrets

adc_admin_password is not written in terraform.tfvars. The variable has no default, so Terraform asks for it, and that single answer is used for every node — the password reset, the cluster resource, the SNIPs and the watcher read the same variable. There is no per-node password to keep in sync.

Every apply and destroy asks twice — the password, then adc_admin_password_confirm — and stops before changing anything if they differ. Terraform cannot tell apply from destroy, so the confirmation is on both. With terraform plan -out=tfplan then terraform apply tfplan, only the plan asks; delete tfplan afterwards — it embeds the password. For unattended runs, export both TF_VAR_adc_admin_password='...' and TF_VAR_adc_admin_password_confirm='...', in single quotes so the shell leaves $ and ! alone, and nothing prompts at all.

What prompting does not do: Terraform does not mask interactive variable input, even for a sensitive variable, so it is echoed as you type. And the value still lands in terraform.tfstate in plaintext — sensitive = true only masks CLI output. What it does do is keep the password out of the file most likely to be committed by accident.

Keep terraform.tfvars, *.auto.tfvars, .terraform/, any saved tfplan and terraform.tfstate* out of git and out of any folder that syncs off this machine. Never commit service-account JSON keys.

Do not press Enter at the password prompt, and watch for stray spaces

Both are specific to typing at a prompt, and both used to fail late and misleadingly, so both are now rejected at plan time by validations in variables.tf:

  • Empty. NITRO answers "Password is not specified" with a non-200, the cluster bootstrap reads every non-200 as "not up yet", and the run dies half an hour later on a timeout that never mentions credentials — see issue 8.
  • Leading or trailing whitespace. Invisible when you re-type it to compare. The reset would set the padded value and later calls would appear to work, until one sends the trimmed one.
  • " or \. JSON can only carry them as escape sequences and NITRO does not decode escapes, so the node would be set to something other than what you typed — or refuse it. Every other special character, & < > included, works.
  • The two answers differ. Caught by the confirmation prompt.

Note that teardown removes nodes from the CLIP before destroying the VMs — so destroy needs the password the nodes actually carry. If it is lost, see Tearing it down: you can still destroy without it.

Boot wait and progress output

Two phases of the apply are long and, by default, completely silent: the boot wait, and the cluster formation. These four settings shorten the first and narrate both. All of them need curl on the Terraform host; all of them skip themselves with a warning if it is missing. They do, however, all require a POSIX shell — see the caveat below.

VariableCurrentNotes
adaptive_boot_waittruePoll each NSIP with a NITRO login (the instance id, no password change) until it answers with anything but errorcode 278, instead of always sleeping the full adc_boot_wait; then wait only adc_boot_settle on top. Typically 3–5 minutes back per apply. Defaults to false — the fixed wait is known-good.
adc_boot_settle90sExtra margin after the probe. The probe now waits for the login handler itself, not just for the web server, and the reset retries a still-booting node on its own — so this rarely matters any more.
adc_boot_probe_timeout900 sPer node, then the probe gives up and lets the apply continue. Half again adc_boot_wait, so a genuinely slow boot is still picked up rather than cut short.
progress_logstrueTimestamped milestone line after each of the six phases. Re-runs every apply by design, so expect six trivial changes in every plan; set false to silence.
cluster_watch_logstrueLogs node state while the cluster forms, rather than after, to cluster_watch.log — not the console, see below. Stops by itself once every node is ACTIVE/UP. Also needs a route to the NSIPs.
cluster_watch_interval / cluster_watch_timeout20 s / 14400 sLines are written on change only, so a short interval costs nothing in noise. The timeout is only a cap — the watcher exits as soon as the cluster is formed — so a generous value costs nothing. The variable's default is 2400; this deployment uses 4 h for 32 nodes.
Where the output goes

Terraform suppresses all output from a provisioner that touches a sensitive value, and the watcher and the password reset both need the password. So they write to files next to the .tf files, and you follow them from a second shell:

tail -f cluster_watch.log                 # live cluster formation
cat password_reset_logs/node0.log          # one per node: each attempt and the ADC's answer

Neither file ever contains the password. The == phase markers from progress.tf touch no secret and still print to the console.

None of this can break an apply

The probe, the six markers and the watcher all create no infrastructure, and nothing in the graph depends on any of them. The probe falls through on timeout; every failure path in the watcher exits 0. Turning them all off changes what you see and nothing about what is built.

One exception, and it is a hard one: all three run through interpreter = ["/bin/sh", "-c"]. A missing curl is handled inside the scripts and costs you nothing; a missing /bin/sh is different, because Terraform then cannot launch the provisioner at all, and a provisioner that fails to start fails the apply. Nothing checks this for you at plan time.

The password reset is not optional in the same way: it needs both /bin/sh and curl, and without either it fails. So run Terraform from Linux, macOS or WSL — plain Windows cannot complete an apply.

The one thing not to do is add citrixadc_cluster.this to the watcher's depends_on. It deliberately shares the cluster's dependencies instead, so Terraform schedules the two together; depending on the cluster would serialise the watcher after the thing it exists to watch, and it would print nothing until the cluster had already finished.

Running it

cd instace_deployment_and_cluster_formation

terraform init
terraform apply              # asks for the ADC password, then again to confirm

The prompt reads:

var.adc_admin_password
  nsroot password for all ADC nodes. Any special character except " and \.
  Asked twice, on apply and destroy. Destroy needs the same password.

  Enter a value:

var.adc_admin_password_confirm
  Type the same password again to confirm.

  Enter a value:

To apply exactly what you reviewed, save the plan: terraform plan -out=tfplan (asks here, and preconditions fire here rather than mid-apply), then terraform apply tfplan (no prompt), then rm -f tfplan — the plan file embeds the password.

Expect roughly 25–45 minutes. Most of it is waiting on hardware that does not report its own readiness:

  • adc_boot_wait — 10 minutes of dead time after the instances exist, before the first NITRO call. With adaptive_boot_wait = true this becomes "however long the boot actually took, plus adc_boot_settle".
  • Bootstrapping node 0 reboots it; the provider polls until it returns.
  • Each node join reboots that node; same again. Node adds are sequential.

With the defaults, the run narrates itself. == lines are phase markers, printed on the console:

==  [09:05:10Z]  2/6  BOOT WAIT COMPLETE  --  NSIPs 172.20.1.11, 172.20.1.12, 172.20.1.13
      next: resetting nsroot from the GCP instance id on each node

==  [09:07:02Z]  3/6  PASSWORDS RESET  --  3 node(s)
      next: forming the cluster. This is the long one -- node 0 bootstraps as
      CCO, then each node joins and REBOOTS. Expect 10-15 min of silence.

==  [09:19:40Z]  4/6  CLUSTER FORMED  --  all 3 node(s) ACTIVE on CLIP 172.20.1.10

Between markers 3 and 4 the console shows only Still creating.... The live detail is the cluster watcher's ~~ lines, in cluster_watch.log (see Where the output goes):

$ tail -f cluster_watch.log
  ~~  cluster watch: polling 172.20.1.11 every 20 s, expecting 3 node(s) ACTIVE/UP
  ~~  [09:07:25Z +23s]   no answer yet from 172.20.1.11 -- node 0 is still bootstrapping or rebooting
  ~~  [09:11:48Z +286s]  node0=ACTIVE/UP
  ~~  [09:16:30Z +568s]  node0=ACTIVE/UP  node1=(Adding)/NOT UP
  ~~  [09:19:02Z +720s]  node0=ACTIVE/UP  node1=ACTIVE/UP  node2=ACTIVE/UP
  ~~  [09:19:02Z +720s]  all 3 node(s) ACTIVE/UP -- cluster formed

A node that sits at (Adding) for several consecutive watcher lines is the backplane failure happening in front of you — you now see it within a minute or two instead of at the 30-minute timeout.

Plan-time preconditions catch the things that would otherwise fail 30 minutes in: CIDRs that do not match reality, an NSIP list the wrong length, a priority range that overflows 31, a CLIP that collides with an NSIP, an invalid backplane interface. Two check blocks warn (without failing) about a new VPC with no peering, and about new networks with no firewall rules.

Verifying the cluster

terraform output cluster_topology   # what Terraform believes it built
terraform output clip
terraform output verify_cluster
terraform output instance_settings  # confirms IP forwarding + cloud-platform scope

Then, from a host on the management network:

ssh nsroot@<clip>
  show cluster instance 1
  show cluster node
  show ns ip
A healthy cluster
  • node_count member nodes, exactly one ACTIVE(Configuration Coordinator)
  • Every node Health: UP, Operational State: ACTIVE
  • No "Heartbeats are not seen on backplane"
  • No "There are no spotted SNIPs configured on the cluster"
  • Sync State not stuck at IN PROGRESS

A node reading (Adding), UNKNOWN or INACTIVE has not really joined. Operational state is gated on health, and health is gated on config sync, which runs over the backplane — so INACTIVE plus a stuck full sync is almost always a backplane symptom.

Things not to change

ThingWhy it is fixed
NIC declaration order in adc_instances.tfGCP attaches NICs in declaration order and the VPX maps them positionally: nic0 → 0/1 management, nic1 → 1/1 client, nic2 → 1/2 server. There is no way to tell a VPX on GCP to use a different NIC for management.
can_ip_forward = trueGCP drops any packet whose source or destination is not the NIC's own address. That would break the CLIP, the striped VIPs, and every steering tunnel. Create-time only; changing it replaces the instance.
scopes = ["cloud-platform"]The default GCE scope set has no compute access and fails with ACCESS_TOKEN_SCOPE_INSUFFICIENT, which reads like an IAM problem and is not one. Only the service-account identity is configurable.
The 32 aliases in providers.tfUnused now, but a state file from before the curl reset needs them to drop its old citrixadc_password_resetter entries. Remove them only once no state anywhere holds those entries.
The reset method in password_reset.tfKeep curl; do not go back to citrixadc_password_resetter. The provider's Go JSON encoder rewrites & < > as \u0026 \u003c \u003e, NITRO does not decode those escapes, and any password containing one fails with errorcode 278 "Invalid argument" on every attempt.
The firewall rules in time_sleep.adc_boot's depends_onThey keep destroy from deleting the rules before the cluster. Without them, nothing depends on the rules, destroy removes them first, the Terraform host loses NITRO to the CLIP mid-teardown, and the destroy fails with Unable to delete cluster node 1: timeout — needing a second run.
The clusternode addsnip optionBroken in the provider through at least 3.0.2 — it reads ownernode from an attribute absent from the resource schema, so the SNIP is always submitted unspotted and the ADC rejects it with errorcode 476. snips.tf works around it. Do not re-enable it.
The depends_on list in cluster_watch.tfIt mirrors citrixadc_cluster.this's own dependencies exactly, which is what makes Terraform run the watcher alongside the cluster. Adding citrixadc_cluster.this to it would serialise the watcher after the thing it reports on, and it would print nothing useful. Likewise, nothing may be made to depend on the markers in progress.tf — their inertness is the reason they are safe to ship enabled.

Common recipes

Deploy into VPCs that already exist

use_existing_networks       = true
existing_management_network = "..."
existing_management_subnet  = "..."
existing_client_network     = "..."
existing_client_subnet      = "..."
existing_server_network     = "..."
existing_server_subnet      = "..."

# These must MATCH the real subnets — a precondition enforces it.
management_subnet_cidr_block = "..."
client_subnet_cidr_block     = "..."
server_subnet_cidr_block     = "..."

# Peering is skipped automatically: if the networks already existed,
# whoever owns them owns their routing.
create_firewall_rules = true   # false only if they already permit what the cluster needs

Pin the addresses instead of deriving them

nsips = ["172.20.1.21", "172.20.1.22", "172.20.1.23"]   # exactly node_count entries
clip  = "172.20.1.20"

Run a second deployment in the same project

prefix                       = "adc-cluster-b"   # every resource name derives from this
management_subnet_cidr_block = "172.21.1.0/24"   # must not overlap the first one
client_subnet_cidr_block     = "172.21.2.0/24"
server_subnet_cidr_block     = "172.21.3.0/24"

Switch the steering mode to GRE

cluster_tunnel_mode = "GRE"   # firewall already permits IP protocol 47

Skip the password reset (nodes already hold the password)

enable_password_reset = false

Tearing it down

terraform destroy            # asks for the password twice, like apply

Answer with the password the nodes actually carry. The order is fixed by the dependency graph: SNIPs and the config save first, then the cluster — every non-CCO node removed from the CLIP, the CCO last — then the instances, and only then the firewall rules, peering and networks. Because the rules and the peering outlive the cluster, NITRO keeps working throughout, and one destroy is enough.

Destroying without the password

The GCP resources do not need it — only the citrixadc_* resources do, and their configuration disappears with the VMs anyway. Make Terraform forget them, then destroy with a placeholder:

cp terraform.tfstate terraform.tfstate.before-rm      # backup first
terraform state list | grep '^citrixadc_' | xargs -r -I{} terraform state rm '{}'
terraform destroy -refresh=false -var adc_admin_password=x -var adc_admin_password_confirm=x

state rm touches neither the ADCs nor GCP; it only edits the state. -refresh=false skips the read that would otherwise fail with 401 on every SNIP.

Known teardown blockers

VPC peerings, regional external addresses and lingering default-route-* routes have each held up a destroy. If it stalls, delete the blocker by hand and re-run — do not delete colleagues' networks in the shared lab project.

terraform.tfstate lives next to these files and is the only record of what exists. Copy it out before syncing anything into this directory. Overwriting it strands every resource in GCP and the next apply fails with 409 alreadyExists on all of them.
