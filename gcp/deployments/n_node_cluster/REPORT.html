What this configuration builds

A single terraform apply that creates node_count NetScaler ADC VPX instances on GCP, resets each node's initial password, and forms them into one NetScaler cluster behind a Cluster IP (CLIP) — with no shell or Python scripts anywhere in the deliverable. It is the merge of two earlier configurations, cluster_3node (clustering, on-prem assumptions) and standalone_3nic (GCP instance plumbing), reconciled for cloud.

Everything in brackets is a report, not a step: the markers and the watcher hang off the graph and nothing hangs off them. cluster_watch is drawn beside citrixadc_cluster.this rather than after it because it shares that resource's dependencies instead of depending on it — which is the only reason it can report while the cluster is still forming.

The single most important structural fact

citrixadc_cluster blocks until every node reports masterstate == ACTIVE. There is no "cluster exists but nodes are still settling" window. Everything below it in the graph runs strictly after the cluster is already healthy — which means no Terraform resource can ever repair an unhealthy node. That one property decided the backplane interface, the firewall rules, and why snips.tf is data-plane-only.

Why the empty-password validation exists

An empty password is accepted by Terraform and is fatal in the most misleading way available. NITRO answers "Password is not specified" with a non-200; the cluster resource's bootstrap poll treats every non-200 as "not reachable yet" and retries until its budget expires. Half an hour later the run fails with timeout waiting for cluster operation to complete and nothing pointing at credentials. Raising the timeout or fixing the network changes nothing, because neither is the problem. Easy to hit by pressing Enter at the interactive prompt.

That prompt is now the normal path — the password is deliberately not set in terraform.tfvars — so this validation is load-bearing rather than a formality. A second validation rejects leading or trailing whitespace, the other way a typed password goes wrong invisibly.

One password, every node

adc_admin_password has no default and is not written to terraform.tfvars, so Terraform asks for it — and then for adc_admin_password_confirm, which must match. That single value is read by password_reset.tf, citrixadc_cluster.this, the SNIPs (through the default provider) and cluster_watch.tf — there is no per-node password anywhere in the configuration, and nothing to keep in sync.

Both prompts come on destroy as well as apply: a variable with no default is required by every command, and Terraform offers no way to tell the two apart. The description is kept to three lines because it is all Terraform prints at the prompt; the long rationale moved to comments above the block.

terraform plan -out=tfplan followed by terraform apply tfplan moves both prompts to the plan, at the cost of a plan file that embeds the password and must be deleted. Exporting TF_VAR_adc_admin_password and TF_VAR_adc_admin_password_confirm removes the prompts entirely. In every case the value still reaches terraform.tfstate in plaintext.

Note what this does not enable: rotation. The reset runs once per instance — its triggers_replace is the instance id — so a changed value at a later apply changes nothing on the nodes, and every NITRO call then fails to authenticate. Change the password on the appliance, then use the new value at the prompt.

Notable defaults

  • node_count = 3 — the only cluster-size knob.
  • backplane_interface = "0/1" — the management interface, deliberately. The heredoc explains the GCP inversion in full.
  • cluster_priority_base = 1 (this deployment overrides it to 0) — was hardcoded at 29 when this only ever built three nodes. 29 + 3 = 32, one past what the ADC accepts. The same arithmetic bites at the top end: since the ADC takes priorities 0–31 and each node gets base + node_id, the real cap is node_count ≤ 32 - base, so a 32-node cluster requires base 0 and uses the entire range.
  • cluster_tunnel_mode = "UDP" — NONE cannot work on GCP's fabric.
  • assign_management_external_ip = false — a public NSIP exposes NITRO and SSH behind one password.
  • adc_boot_wait = "600s" — 300s was too short.
  • adaptive_boot_wait = false — the probe is the faster path, but the fixed wait is the known-good one, so the default is the conservative choice rather than the quick one.
  • adc_boot_settle = "90s" — only used with the probe on; extra margin after it. The probe now waits for the login handler rather than mere liveness, and the reset retries a still-booting node itself, so this rarely matters.
  • progress_logs = true, cluster_watch_logs = true — on by default, because neither can affect the apply and a silent 25-minute run is hard to debug.
  • cluster_watch_timeout = 2400 (this deployment overrides it to 14400 for 32 nodes) — past citrixadc_cluster's own 30m budget, so the watcher never goes quiet while the thing it watches is still running. Only a cap: the watcher exits as soon as every node is UP.

locals.tf152 lines

The scaling hub. Every per-node list in the configuration is computed here, so adding a node is a change in one place that propagates everywhere.

Node set

node_count = var.node_count
node_ids   = range(local.node_count)
max_nodes  = 32              # size of the provider-alias pool

Network resolution — two modes, one name

management_network_name = coalesce(
  one(data.google_compute_network.management[*].name),     # existing mode
  one(google_compute_network.management_network[*].name),  # created mode
)

one() yields null for an empty (count = 0) list and the single element otherwise, so coalesce picks whichever mode produced a value. A plain ternary fails here, because indexing the inactive side's empty list errors even on the branch not taken. The same pattern resolves self-links and CIDRs for all three networks.

Addressing

nsips      = var.nsips != [] ? var.nsips
           : [for i in node_ids : cidrhost(management_cidr_block, nsip_host_offset + i)]
client_ips = [for i in node_ids : cidrhost(client_cidr_block, data_host_offset + i)]
server_ips = [for i in node_ids : cidrhost(server_cidr_block, data_host_offset + i)]
clip       = var.clip != "" ? var.clip : cidrhost(management_cidr_block, clip_host_offset)
Derived from the variables, never from the data sources

A provider configuration cannot depend on a data source read, so the citrixadc endpoints must be known at plan time. That is why the addresses come from the declared CIDR blocks. The cost is that the declared CIDRs can drift from reality in existing-networks mode — which is exactly what the first three preconditions in adc_instances.tf catch.

The provider endpoint pool

provider_endpoints = [
  for i in range(local.max_nodes) :
  i < local.node_count ? local.node_endpoints[i] : "http://127.0.0.1"
]

Feeds the 32 aliases in providers.tf, which nothing uses since the curl reset but which stay for old state (see below). Always 32 entries, whatever node_count is: Terraform evaluates every provider block in the configuration at plan time, used or not, so a shorter list fails on an index-out-of-range. Inactive slots get loopback rather than a derived address — they are never dialled, and pointing them at cidrhost() output would let a small management subnet break the plan over an alias nothing uses.

Cluster node objects

cluster_nodes = [
  for i in node_ids : {
    nodeid    = i
    ip        = nsips[i]
    priority  = var.cluster_priority_base + i      # lowest wins the CCO election
    backplane = "${i}/${var.backplane_interface}"  # 0/0/1, 1/0/1, 2/0/1 ...
    snip_address = server_ips[i]
    snip_netmask = server_netmask
  }
]

The backplane string is <nodeid>/<slot>/<port>, which is why the variable holds only the slot/port half.

Also here: create_peering (1 only when we created the management network ourselves and peer_network is set), and client_netmask / server_netmask — cidrnetmask() conversions, because GCP talks CIDR and NITRO wants a dotted quad.

providers.tf294 lines — generated

Three kinds of provider block.

  1. google — project and region.
  2. Default citrixadc — endpoint is local.cluster_api_endpoint, i.e. the CLIP. Used by citrixadc_cluster and everything in snips.tf. do_login = false, because the CLIP does not exist at configure time; the first real connection happens during the bootstrap poll, by which point the CCO has it up.
  3. 32 aliases node0…node31 — each pointing at local.provider_endpoints[N]. Written for the 32 citrixadc_password_resetter blocks the reset used to be; nothing uses them now.
provider "citrixadc" {
  alias    = "node7"
  endpoint = local.provider_endpoints[7]
  username = var.adc_admin_username
  password = var.adc_admin_password
  do_login = false
}
Why the aliases stay although nothing uses them

They were forced: citrixadc_password_resetter carries no endpoint of its own — its whole schema is username / password / new_password — so the only way to aim it at a node was a provider alias, and Terraform cannot generate aliases. The reset is now terraform_data.password_reset (see password_reset.tf), which needs no provider at all.

They stay because Terraform needs a resource's provider configuration to remove it from state, and a state file from before the change may still hold citrixadc_password_resetter.nodeN entries. Delete the aliases only once no state anywhere holds those entries. Until then, nothing in this file is meant to be read or edited.

They cost nothing: do_login = false, unused slots point at loopback, and no resource references them, so no connection is ever attempted.

network.tf279 lines

Three networks, two modes

Each NIC of a GCE instance must sit in a different VPC — GCP does not allow two NICs of one instance on the same network — so this deployment always needs exactly three, regardless of node count.

use_existing_networksBehaviourQuota
falseCreates 3 google_compute_network + 3 google_compute_subnetwork, all with auto_create_subnetworks = false and private_ip_google_access = true3 of 50 per project

Both sets always exist in the configuration, counted 1/0 off local.create_networks / local.lookup_networks; locals.tf collapses them to one name per network.

Five firewall rules

management_backplane_firewall is load-bearing

The management subnet is also the cluster backplane, so heartbeats and UDP steering tunnels ride it. The original management rule listed icmp plus a handful of TCP ports and no UDP at all. Allow rules are purely additive, so nothing flagged the gap — every UDP steering packet between nodes was silently dropped, and the apply spent 30 minutes waiting for a node to go ACTIVE before failing with a bare timeout. This rule is scoped to the management CIDR, so it opens nothing beyond the nodes to each other.

Four of the rules — management, management-backplane, server and cluster-backplane — are listed in time_sleep.adc_boot's depends_on in adc_instances.tf. That is about destroy order: see below.

Two check blocks — warnings, not errors

These are the two configurations that produced a successful plan, built every resource, and then failed on an i/o timeout with no hint of the real cause:

  • terraform_can_reach_the_nsips — new VPCs, no peer_network, no node_endpoints override. A new VPC is isolated; the Terraform host will have no route to the NSIPs.
  • new_networks_have_firewall_rules — new VPCs with create_firewall_rules = false. A new network permits no ingress at all.

External addresses

google_compute_address.management_external_address and client_external_address, each counted at local.node_count when its assign_* flag is true. Client addresses are per node because a cluster VIP is striped across every node — there is no single external address that represents the cluster.

peering.tf50 lines

Three resources, active only when local.create_peering == 1 (we created the management network and peer_network is set — if the networks already existed, whoever owns them owns their routing):

  • data.google_compute_network.peer
  • google_compute_network_peering.mgmt_to_peer
  • google_compute_network_peering.peer_to_mgmt — depends_on the first
Both directions are required

A one-sided peering stays INACTIVE and routes nothing. They are sequenced rather than created in parallel because GCP intermittently rejects the second half of a simultaneous pair.

Requirements recorded in the file header:

  • The two networks must not have overlapping CIDRs — peering is refused outright if they do. This is why the defaults live in 172.20.x rather than the 10.0.x space the rest of the project uses.
  • You need permission to create a peering on both networks; the reverse peering modifies the peer network's routing.
  • Peering does not carry firewall state — management_firewall must allow controlling_subnet.
  • Peering is not transitive: only hosts on peer_network itself get a route.

NIC order is significant and must not be rearranged

nic0 -> ADC 0/1   management  (NSIP, CLIP alias on node 0, cluster backplane)
nic1 -> ADC 1/1   client      (VIP)
nic2 -> ADC 1/2   server      (SNIP)

GCP attaches NICs in declaration order and the VPX maps them positionally. There is no way to tell a VPX on GCP to use a different NIC for management; the first one always wins.

Each NIC pins network_ip from the matching locals.tf list, so the addresses are known at plan time. access_config blocks are dynamic on the assign_*_external_ip flags. The CLIP is published as an alias_ip_range of ${clip}/32 on nic0 — but only on count.index == 0, because GCP only delivers traffic to addresses it has been told about.

CLIP alias caveat

The alias is pinned to node 0 and does not follow a CCO failover. If node 0 loses the CCO role, the CLIP stops being reachable from elsewhere in the VPC until the alias is moved.

Eight preconditions, all evaluated at plan time

#Checks
1–3Each declared *_subnet_cidr_block matches the real subnet. Needed because the addresses derive from the variables, not the data sources.
4nsips is empty or exactly node_count long
5node_endpoints is empty or exactly node_count long

Checks 4–7 are preconditions rather than variable validations because each compares several variables to one another, which variable validation could not do before Terraform 1.9 — and versions.tf was at 1.5 when they were written. The floor is 1.9 now, but they work the same as preconditions and were left alone.

terraform_data.nitro_probe — optional, off by default

count            = var.adaptive_boot_wait ? 1 : 0
depends_on       = [adc instances, mgmt_to_peer, peer_to_mgmt]
triggers_replace = join(",", google_compute_instance.adc[*].instance_id)

The fixed wait below is sized for the worst case — a VPX "regularly needs 6–10 minutes", so adc_boot_wait is 600s and every apply pays all of it, including the ones where the appliance was answering at minute five. This probe, for each NSIP in turn, logs in with the instance id and no new_password until NITRO answers with any errorcode other than 278 — typically 1046, "ForcePasswordChange is enabled" — so the wait costs what the boot costs. The login changes nothing on the node.

It used to stop at the first HTTP answer from /nitro/v1/config/nsversion. That proved too early: the VPX web server answers minutes before its login handler can take a password change, and in that gap every login returns errorcode 278 "Invalid argument". On timeout the probe now also prints the last answer it got.

It sits before time_sleep rather than replacing it, which keeps the graph identical downstream:

instances + peering ──> nitro_probe ──> time_sleep.adc_boot ──> password_reset

time_sleep.adc_boot keeps its address, so the depends_on references to it in password_reset.tf, cluster.tf, cluster_watch.tf and progress.tf are untouched. Same triggers_replace keying as the sleep: a new instance means a new probe.

It cannot fail an apply that would otherwise have succeeded

On timeout it prints a warning and exit 0s, leaving the apply to continue and the password reset to report the real error. On a host with no curl it sleeps the full adc_boot_wait instead — exactly the behaviour it replaced. With adaptive_boot_wait = false it is count = 0, and a depends_on against a count = 0 resource is simply satisfied.

adc_boot_settle still adds its margin afterwards, and the password reset retries a node that answers 278 on its own, so a probe that returns marginally early costs nothing.

One caveat applies to this and to the progress and watch files: the provisioner is interpreter = ["/bin/sh", "-c"]. A missing curl is handled inside the script; a missing /bin/sh is not, because Terraform cannot launch the provisioner at all and a provisioner that fails to start fails the apply. The password reset needs both /bin/sh and curl outright — so the Terraform host must be Linux, macOS or WSL in any case.

time_sleep.adc_boot

depends_on = [adc instances, mgmt_to_peer, peer_to_mgmt,
              management_firewall, management_backplane_firewall,
              server_firewall, cluster_backplane_firewall,
              terraform_data.nitro_probe]
triggers   = { instance_ids = join(",", google_compute_instance.adc[*].instance_id) }
create_duration = var.adaptive_boot_wait ? var.adc_boot_settle : var.adc_boot_wait
                  #          90s settle                          600s worst case

The ADC takes several minutes past instance creation before its management interface answers NITRO, and nothing in the GCP API reports that. Peering is in the depends_on too — the route must exist before the first NITRO call, and nothing else in the graph forces that ordering.

The firewall rules are here for destroy, more than create

Every NITRO resource sits downstream of this one, so on destroy it goes late and the rules after it. Before they were listed, nothing depended on the rules at all, and destroy deleted them in its opening seconds — in parallel with the cluster. The management rule is what lets the Terraform host reach the CLIP. With it gone, citrixadc_cluster's Delete removed node 1 and then polled the CLIP (GET /nitro/v1/config/nslicense, waiting for a 200) for its full clip_migration_total_timeout, and failed with Unable to delete cluster node 1: timeout waiting for cluster operation to complete. A second destroy then succeeded, because the removal itself had gone through and only the CCO — whose delete does not poll — was left.

On create the same dependency guarantees the rules exist before the first NITRO call, which had only been true by timing.

The triggers block matters: without it the wait happens exactly once, ever. depends_on orders the graph but does not force replacement, so rebuilding an instance later (-replace to clear a half-formed cluster off a node, say) would leave the sleep already satisfied in state and fire the first NITRO call at a node still booting.

password_reset.tf119 lines

A NetScaler ADC booted from a GCP image comes up with its nsroot password set to the GCP instance id, and refuses every other NITRO call until that password is changed. This makes that change, against each node's own NSIP — or its node_endpoints override — before the cluster resource runs.

resource "terraform_data" "password_reset" {
  count            = var.enable_password_reset ? local.node_count : 0
  triggers_replace = google_compute_instance.adc[count.index].instance_id
  depends_on       = [time_sleep.adc_boot]

  provisioner "local-exec" {
    interpreter = ["/bin/sh", "-c"]
    environment = {
      NODE_URL  = trimsuffix(local.node_endpoints[count.index], "/")
      ADC_USER  = var.adc_admin_username
      BOOT_PASS = google_compute_instance.adc[count.index].instance_id
      NEW_PASS  = var.adc_admin_password
      DEADLINE  = local.reset_timeout                 # 600 s
      LOG       = "${path.module}/password_reset_logs/node${count.index}.log"
    }
    command = <<-EOT ... EOT                         # curl, see below
  }
}
Why curl, and not citrixadc_password_resetter

This file used to be 32 citrixadc_password_resetter blocks. That resource builds the login body with Go's json.Marshal, which rewrites & < > as \u0026 \u003c \u003e. NITRO does not decode \u escapes, so any password containing one of those three characters failed with errorcode 278 "Invalid argument" — on every attempt, however long the node had been up, which made it look like a timing problem. Tested against the VPX:

Sent to NITROResult
raw Ab&c<d>e!@#$%^*()-_=+[]{};:,.?/~`|1set OK, login OK
\u0061 in place of a354 — the escape is not decoded
\" or \\ (JSON escapes)rejected; cannot be set

So the body is written here with printf, byte for byte, and " and \ — which JSON cannot carry without the escapes NITRO mishandles — are refused up front by a validation on adc_admin_password.

The reset loop

Per node, every 15 s until DEADLINE:

  1. Log in with adc_admin_password. Accepted → already done, exit 0. This makes the resource idempotent: a re-run against a finished node is a no-op.
  2. Log in with the instance id plus new_password — the normal first-boot path.
  3. Log in with the instance id alone. Accepted → the image has no forced change pending (some custom images), so set the password with PUT /nitro/v1/config/systemuser on that session instead.

A 278, or no answer at all, means the node is still coming up; the loop simply tries again. Past the deadline it exits 1 and the apply fails on this resource.

ChoiceWhy
Password to curl on stdin (--data-binary @-)Never on a command line, so never in ps. It is in terraform.tfstate in plaintext either way.
Progress to password_reset_logs/node<N>.logTerraform suppresses all output of a provisioner that touches a sensitive value, and NEW_PASS is one — so nothing printed would reach the console. The log holds each attempt's errorcode and message; the password is never written to it.
triggers_replace = the instance idA new instance means a new boot-time password, so a new reset. Nothing else re-runs it — which is also why changing the variable later does not rotate the password.
Aims at local.node_endpointsThe NSIP by default; the node_endpoints override when set, as the old resetter's provider aliases did.
One counted resource, not 32 blocksIt needs no provider, so nothing forces one block per alias. count = 0 when enable_password_reset = false.

cluster.tf123 lines

One composite resource, citrixadc_cluster.this, which does three things in order:

  1. Bootstrap node 0 as the Cluster Configuration Coordinator (CCO)
  2. Create the Cluster IP (CLIP)
  3. Declare each remaining node on the CLIP, then join it — sequentially

Timeouts

bootstrap_poll_delay    = "180s"   node_add_poll_delay    = "180s"
bootstrap_poll_interval = "30s"    node_add_poll_interval = "30s"
bootstrap_poll_timeout  = "30s"
bootstrap_total_timeout = "30m"    node_add_total_timeout = "30m"

clip_migration_poll_timeout  = "30s"     # destroy: per-request, after each node removal
clip_migration_total_timeout = "20m"     # destroy: provider default is 10m

Both enable cluster instance on the CCO and each node join reboot the node in question, and the provider polls until it returns. These budget for a reboot, not an API call: this VPX needs the full 10 minutes of adc_boot_wait just to come up cold, so the provider's 10m default expires while the node is still booting and reports the bootstrap as failed when it is merely slow. poll_delay is dead time before the first poll; poll_timeout is the per-request HTTP timeout, and the 10s default is tight for a VPX answering slowly mid-boot — a timed-out poll is indistinguishable from a refused one.

The clip_migration_* pair governs destroy: the provider's Delete removes each non-CCO node, then polls the CLIP until it answers 200 again. The per-request timeout gets the same reasoning as above; the total is raised from 10m only as margin. A CLIP that never comes back is the firewall ordering covered under time_sleep.adc_boot, not something time fixes.

dynamic "clusternode"

One block per entry in local.cluster_nodes: nodeid, endpoint (http://<nsip>), ipaddress, backplane, priority, state = "ACTIVE", tunnelmode, nodegroup = "DEFAULT_NG", plus explicit username/password — these default to the provider block, but the provider block points at the CLIP while these calls go to the node's own NSIP.

addsnip is deliberately not set, and must not be

It looks like exactly what this deployment needs — it adds the node's backplane address to the CLIP as a SNIP before the node joins — but it is broken in the provider. In resource_citrixadc_cluster.go:

if raw := d.GetRawConfig().GetAttr("ownernode"); !raw.IsNull() {
    nodeNsip.Ownernode = intPtr(d.Get("ownernode").(int))
}

d is the top-level cluster resource, and ownernode is not in that resource's schema — those two lines are its only occurrences in the file. The branch is never taken, Ownernode is never set, and the SNIP goes to the appliance unspotted. The Framework rewrite (citrixadc_framework/cluster/resource_cluster.go) does not even attempt it: its addsnip payload has no Ownernode field at all. On a cluster the ADC refuses an unspotted SNIP outright — errorcode 476, "Owner node is not specified." — which killed an apply. No value in this configuration can change that. snips.tf does it instead.

The blocking behaviour, and what it rules out

After joining a node, the resource polls the CLIP until that node's masterstate reads ACTIVE, and does not return until every node does (pollClusterNodeWithid in the provider source). There is no "cluster formed, nodes still settling" moment — anything that depends_on this resource runs strictly after all nodes are healthy.

That rules out fixing an unhealthy node from Terraform. A node whose backplane has no IP never leaves (Adding); the poll runs out its 30 minutes and the apply dies on a bare timeout waiting for cluster operation to complete. The SNIP that would have given it an address sits unapplied in the graph behind the very resource waiting for it. Hence the backplane on 0/1, which already has the NSIP.

depends_on: every password reset

depends_on = [terraform_data.password_reset, time_sleep.adc_boot]

A reference to the whole counted resource covers every node, whatever node_count is. A missing dependency here would not look like one: it would surface half an hour later as this resource timing out against a node still holding its GCP instance id as its password.

snips.tf101 lines

GCP puts an address on each instance's nic1 and nic2, but a VPX auto-configures only its NSIP, from nic0. Interfaces 1/1 and 1/2 come up with no IP at all unless something adds one — which is why the CCO reported "There are no spotted SNIPs configured". These are the data-plane addresses: without them the appliance can be managed but cannot pass traffic.

ResourceCountAddressGives
citrixadc_nsip.server_snipconfigure_server_snips ? node_count : 0local.server_ips[i]interface 1/2 an IP, so the node can reach back-end servers
citrixadc_nsip.client_snipconfigure_client_snips ? node_count : 0local.client_ips[i]interface 1/1 an IP, so the data plane can originate and answer

Both set type = "SNIP", ownernode = count.index and icmp = "ENABLED" (the quickest way to confirm from inside the VPC that the SNIP landed on the node that owns it). Both run against the CLIP — the default provider endpoint — once the cluster exists, because that is the point at which ownernode has a meaning.

Why they must be spotted

"Spotted" means the IP belongs to exactly one node. In cloud it has to be: GCP delivers 172.20.3.12 to node 1's nic2 and nowhere else, so a striped SNIP would have every node answering for an address only one of them can actually receive. ownernode is what makes it spotted, and on a cluster the ADC rejects an unspotted one with errorcode 476. The index is the node id by construction — local.client_ips is built in node-id order from the same expression that assigns network_ip on nic1.

Nothing here helps the backplane

Trying to make it was the second failed apply. citrixadc_cluster does not return until every node reports ACTIVE, so a resource that depends on it cannot run while a node is still stuck (Adding) for want of a backplane address.

citrixadc_nsconfig_save.cluster

Everything above, and everything the cluster resource did, lives in the running configuration only. Cluster nodes reboot on their own — during a CCO failover, or when an operator reboots one — and a node that comes back without this config loses its backplane address and drops out again. A save issued on the CLIP writes ns.conf on every node, so one of these covers all of them.

timestamp = sha1(join(",", concat(
  [tostring(var.cluster_id), local.clip],
  local.nsips, local.server_ips,
  var.configure_client_snips ? local.client_ips : [],
)))

concurrent_save_ok       = true
concurrent_save_retries  = 5
concurrent_save_interval = "20s"
concurrent_save_timeout  = "5m"

The timestamp hash is what forces a re-save: the resource is otherwise unchanged between applies and would be skipped. Keying it on the cluster identity and the addresses means a re-save whenever any of that is rebuilt and not otherwise — timestamp() itself is deliberately avoided, since it would produce a permanent diff on every plan. The concurrent_save_* settings exist because another node may be mid-save when this runs: the join of the last node triggers an internal sync, and a transient "save in progress" should retry rather than fail the apply.

progress.tf106 lines

Terraform reports per-resource progress — "Creation complete after 45s" — but nothing about where the apply is as a whole, which is unhelpful on a run that takes 20+ minutes and spends most of it inside two resources that print nothing while they poll. Six markers print a timestamped line as each phase completes.

ResourceFires afterPrints
progress_instancesgoogle_compute_instance.adc1/6 INSTANCES CREATED + the run's shape: node count, cluster id, CLIP
progress_boottime_sleep.adc_boot2/6 BOOT WAIT COMPLETE + the NSIPs

Each line also names what happens next, so the silence that follows is expected rather than alarming. progress_passwords depends on the whole counted reset resource, the same reference cluster.tf uses, so the marker cannot fire before the last reset has finished.

These are the only provisioners here that print to the console: they touch no sensitive value. The reset and the watcher both need the password, so Terraform suppresses their output and they write to log files instead.

terraform_data, and timestamp() on purpose

terraform_data rather than null_resource: it is built into Terraform 1.4+, so it adds no provider to required_providers and no download to terraform init. versions.tf already requires 1.9.

triggers_replace = timestamp() means every marker re-runs on every apply. That is the point — a marker that fires once is useless as a progress indicator — but it does mean six trivial changes in every plan. Note the contrast with citrixadc_nsconfig_save above, where timestamp() is deliberately avoided: there a permanent diff would re-run real work, here it re-runs an echo. Set progress_logs = false to silence them.

cluster_watch.tf131 lines

citrixadc_cluster.this blocks for 10–15 minutes and prints nothing but "Still creating...". All the interesting state — which node has been declared, which is rebooting, which has gone ACTIVE — lives on the CCO and is only visible if something asks. This asks.

password_reset + time_sleep ───> citrixadc_cluster.this (does the work) └──> cluster_watch (reports on it)

The depends_on list is identical to the cluster resource's own — terraform_data.password_reset plus time_sleep.adc_boot — and nothing depends on the watcher. That is what makes Terraform schedule the two together instead of in sequence. Adding citrixadc_cluster.this to the list would serialise the watcher after the thing it is supposed to be watching, and it would have nothing left to report.

ChoiceWhy
Polls node 0's NSIP, not the CLIPThe CLIP does not exist until node 0 has finished bootstrapping, and the first few minutes are exactly what you want to see.
GET /config/clusternode, read-onlyIt cannot affect what the cluster resource does.
Parsed with tr and sed — no jq, no PythonWorks on a bare VM. One node object per line, then nodeid / masterstate / health out of each. The patterns allow the space NITRO writes after each colon ("nodeid": 0) and a quoted or bare nodeid. They originally required "nodeid":"0", matched nothing, and the watcher ran out its whole cluster_watch_timeout — hours — on a cluster long since formed.
Writes to cluster_watch.log, not the consoleTerraform suppresses all output of a provisioner that touches a sensitive value, and the watcher needs the password. Follow it with tail -f cluster_watch.log.
Writes on change onlyA heartbeat every 20s would bury the three or four transitions that actually tell you something.
Shows NITRO's message when it finds no nodecluster instance not created yet (NITRO: Invalid username or password) points straight at a password problem, where the bare line did not.
Credentials passed via environment, not the command lineThey do not show up in ps on the Terraform host. They are in terraform.tfstate in plaintext either way.

terraform.tfvars / terraform.tfvars.example

The live control panel and its sanitised template. Both are heavily commented — the comments are where the operational knowledge lives, including the pre-apply checks (VPC quota, image validation) and the warning that terraform.tfstate sits next to them and is the only record of what exists.

FileRole

Keep out of version control

terraform.tfvars, *.auto.tfvars, .terraform/, terraform.tfstate*, any saved tfplan, password_reset_logs/, cluster_watch.log, and any service-account JSON key. (The two logs never contain the password, but they are run artefacts, not source.) The password lands in state in plaintext regardless of sensitive = true, which only masks CLI output — and a saved plan file embeds it too, which is the cost of using plan -out to avoid re-prompting.
